Ce qui change réellement

Trois divergences sémantiques entre encoding/json et encoding/json/v2 touchent ce dépôt. Elles ont été mesurées, pas supposées : voici la sortie réelle des deux moteurs sur la même structure.

Sortie observée · même struct, deux moteurs
v1: {"sl":null,"m":null,"str":"x","html":"&"}
v2: {"sl":[],  "m":{},  "str":"x","html":"<b>&</b>","n":0}
                ↑ tableau vide  ↑ objet vide      ↑ plus d'échappement HTML   ↑ omitempty ignoré
A

omitempty n'omet plus les zéros numériques, booléens ni temporels

En v2, omitempty signifie « omettre si l'encodage JSON est vide » : 0 et false ne le sont pas. Les pointeurs, chaînes, slices et maps gardent le comportement attendu — ce qui limite l'impact à deux champs dans tout le domaine.

Les seuls champs non-pointeurs concernés
- internal/domain/analysis.go:55  StatusCode int  `json:"status_code,omitempty"`
+ internal/domain/analysis.go:55  StatusCode int  `json:"status_code,omitzero"`

- internal/domain/mail.go:181     Individuel bool `json:"individuel,omitempty"`
+ internal/domain/mail.go:181     Individuel bool `json:"individuel,omitzero"`

Data any (handler.go:86) et Language i18n.Lang (tenant.go:20, type string) restent corrects tels quels.

B

Les slices et maps nulles sérialisent en [] et {}

Changement visible par le frontend React. Il concerne les champs sans omitempty : Rules, Issues, Clients, Links (analysis.go), Variables et Data (template.go), Items (mail.go:224).

C'est une amélioration du contrat d'API — plus de null à garder côté React — mais elle doit être assumée explicitement, pas subie. json.FormatNilSliceAsNull(true) permet de conserver l'ancien comportement si la rupture n'est pas souhaitée maintenant.

C

Le décodage devient sensible à la casse et refuse les clés dupliquées

{"STR":"hi"} ne remplit plus le champ str — et n'échoue pas non plus : le membre est simplement ignoré, donc silencieusement perdu. Un client qui envoie Template_ID au lieu de template_id verra ses requêtes acceptées mais amputées.

Les clés dupliquées, elles, deviennent une erreur dure : jsontext: duplicate object member name "str".

Deux intégrations à recâbler

Point non évident nº 1 — Echo ne passe pas par vos imports

Tous les c.JSON(...) traversent echo.DefaultJSONSerializer, qui est câblé sur encoding/json v1. Aucun sérialiseur personnalisé n'est enregistré aujourd'hui. Changer les imports dans internal/handler/ ne changera donc rien aux réponses HTTP : il faut implémenter echo.JSONSerializer et l'installer sur l'instance créée en cmd/mailhive/main.go:318.

Point non évident nº 2 — les types d'erreur JSON changent

bindRequest (internal/handler/handler.go:25-70) traduit les erreurs JSON en messages i18n en s'appuyant sur *json.SyntaxError et *json.UnmarshalTypeError. Ces types ne sont plus retournés par v2 ; le mapping i18n doit être réécrit, sinon toutes les erreurs de body retombent silencieusement sur le message générique err.invalid_json.

Correspondance vérifiée des types d'erreur
v1  *json.SyntaxError        .Offset
v2  *jsontext.SyntacticError .ByteOffset  .JSONPointer  .Err
    jsontext: invalid character 'b' at start of value after offset 1

v1  *json.UnmarshalTypeError .Field  .Type  .Value
v2  *json.SemanticError      .JSONPointer  .GoType  .JSONKind  .ByteOffset
    json: cannot unmarshal JSON string into Go int within "/n"

Le nom de champ pour FieldValidationError se dérive désormais du JSONPointer ("/n") plutôt que de .Field, et i18n.TypeName se nourrit de GoType.Name() côté attendu, JSONKind.String() côté reçu. toSnakeCase devient inutile sur ce chemin : le pointeur porte déjà le nom JSON.

Les sept étapes

00

Filet de sécurité avant tout changement

aucun risque

Cette étape est la condition de toutes les autres : capturer le contrat d'API actuel pendant qu'il tourne encore sur v1.

  • Tests golden figeant la sortie JSON de chaque struct de réponse (MailResponse, TemplateResponse, SpamResult, HTMLCompatResult, LinkCheckResult, Paginated[T]…), y compris les cas slice nulle et map nulle.
  • Tests figeant les corps d'erreur de bindRequest (JSON malformé, mauvais type) dans les deux langues.
  • make test-all vert enregistré comme référence.
01

Toolchain 1.27 et cohérence des versions

risque faibleaucun changement de comportement

Le dépôt est déjà incohérent aujourd'hui : go.mod déclare 1.25.0 alors que le Dockerfile compile sur golang:1.26-alpine. Cette étape aligne tout.

  • go.mod : go 1.25.0 → go 1.27.0, plus une directive toolchain go1.27.0.
  • Dockerfile:18 : golang:1.26-alpine → golang:1.27-alpine.
  • La CI et GoReleaser utilisent déjà go-version-file: go.mod — rien à toucher.
  • Vérifier : go build ./..., go vet ./..., make test-all.

03

json/v2 sur la couche interne

risque moyendonnées persistées

D'abord les encodages qui ne sortent pas de l'application : payloads Asynq, colonnes JSONB, corps compressés, journal d'audit.

  • internal/compress/body.go — omitempty sur deux string, sémantique inchangée.
  • internal/worker/{tasks,server,mail_handler}.go — payloads Asynq.
  • internal/adapter/postgres/{mail,template,tenant}_repo.go — colonnes JSONB.
  • internal/service/llm_service.go, internal/middleware/audit.go.
Ordre de déploiement

Les tâches Asynq déjà en file ont été encodées par v1. Le décodage v2 reste compatible tant que la casse des tags correspond exactement — c'est le cas ici, mais la marge est nulle. Purger la file avant bascule, ou déployer le worker après l'API, plutôt que de compter dessus.

04

json/v2 sur la couche HTTP

risque élevécontrat d'API

Le cœur de la migration, et la seule étape où le contrat public bouge.

  • Implémenter echo.JSONSerializer (Serialize / Deserialize) sur encoding/json/v2 et l'installer sur e := echo.New() — cmd/mailhive/main.go:318. jsontext.WithIndent couvre le paramètre indent de l'interface.
  • Réécrire le mapping d'erreurs de bindRequest sur *jsontext.SyntacticError et *json.SemanticError (voir la table de correspondance plus haut).
  • Adapter jsonContextAt : .Offset → .ByteOffset.
  • Décider explicitement du sort de MatchCaseInsensitiveNames : l'activer pendant une version de transition préserve le comportement v1 pour les clients existants, et permet de retirer la tolérance plus tard, une fois annoncée.
  • Les tests golden de l'étape 00 doivent maintenant échouer exactement là où le changement est voulu — chaque écart non anticipé est un bug.
05

Audit des tags : omitempty → omitzero

risque moyen92 tags à passer en revue
  • Corriger les deux champs cassants (StatusCode, Individuel).
  • Passer les champs pointeurs (*bool, *int, *float32, *time.Time, *uuid.UUID) en omitzero : le résultat est identique mais l'intention devient lisible.
  • Conserver omitempty sur les chaînes, slices et maps — c'est là que sa sémantique « vide » reste la bonne.
  • Côté React : les tableaux arrivent désormais en []. Les gardes ?? [] deviennent superflues ; les retirer est optionnel, le typage TypeScript peut en revanche être resserré.
